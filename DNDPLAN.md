## 0. How to work on this project (instructions for Claude Code)

1. **First, create `CLAUDE.md`** in the repo root. Summarize the architecture, the commands (`npm run dev/test/e2e/validate:campaigns/build`) and the rules below so later sessions pick up fast.
2. **Ask the owner before starting** for anything listed in §17 ("Things to ask the owner"), especially API keys for the real-run screenshot pass.
3. **Testing is mandatory.** Every module gets Vitest unit tests as you write it, and every phase ends green. Use Playwright for end-to-end flows. Mock AI providers *in tests only*.
4. **No placeholder assets.** Every icon, image, sound and music file that ships must be real and finished: hand-built SVG, CC0-licensed audio with recorded provenance, or audio you generate yourself (see §11). No "TODO image", grey boxes or lorem ipsum in shipped UI.
5. **No secrets in the repo.** Keys live only in the user's browser, or in `.env.local` (gitignored) for your own dev and screenshot runs.
6. **Don't hard-code model IDs from memory.** Fetch each provider's model list from its API at runtime (`GET /v1/models` or equivalent) and let the user pick. Defaults are stored as settings and can be changed.
7. Prefer small, well-named modules. Keep the game engine pure TypeScript with no React, so it's fully unit-testable.

## 1. Product summary

A browser app where an **AI Dungeon Master** runs a **30–60 minute tabletop RPG campaign** for **1–4 players sitting at the same computer**. The DM speaks aloud with high-quality text-to-speech. Players answer by **microphone or keyboard**. While the game runs, the app shows **AI-generated images** of the characters and scenes, a **live roster** of who's in the scene, a **game-state panel**, **ambient music**, and **dice**: animated 3D dice, or physical dice whose result the player types in.

Campaigns are **plain-text content packs**: a fixed set of markdown files the owner can write by hand or with Claude offline. So any genre works: medieval fantasy, 1920s–30s noir, space exploration, and so on.

**Hosting:** a static single-page app deployed to **GitHub Pages** from the owner's GitHub account. There's no backend. API keys are entered once in Settings, stored in the browser, and calls go directly from the browser to each provider.

**Two models, two jobs:**
- **Building the app:** Claude Fable 5.2 (you).
- **Running the game:** a cheaper, creative model chosen in Settings. The default is **Claude Sonnet 5.5** (`claude-sonnet-5-5`) for the DM and **Claude Haiku 5.5** (`claude-haiku-5-5`) for the background helpers (image prompts, recaps, summaries). The DM model can be switched **mid-game** from the top bar.

## 4. Screens & flow

1. **First-run setup wizard** (runs once, re-openable from Settings):
   API keys per provider (each with a "Test connection" button) → choose default DM model and helper model (from live model lists) → voice provider + narrator voice (with a "Preview" button) → speech input mode → image provider + model → music volume → done.
   Settings persist in IndexedDB. **Settings → Export / Import** saves everything to a JSON file (key export is optional and off by default) so setup is never lost. Optional: encrypt stored keys with a passphrase (WebCrypto AES-GCM).

2. **Home**: Continue saved session · New game · Load recap file · Campaign library · Settings.

3. **New game setup** (one structured flow, repeated per player):
   - Number of players (1–4).
   - **Campaign picker**: cards with key art, genre, tone, length and short pitch.
   - **Dice mode**: *Digital dice* / *Physical dice* / *Per player* (each player picks). Can be changed mid-game.
   - **Character creation** for each player, using the shared questions in `character-creation.md` (§8). Any optional answer can be "Surprise me" (the AI fills it in to fit the campaign).
   - **Review party** → **Begin**. Portrait generation starts the moment each character is confirmed, not when everyone is done, and a party shot is queued as soon as all portraits exist.

4. **Game table** (main screen, §5).

5. **Pause / Save & quit** → writes the autosave and the **recap.md** (§12), and offers to download it.

6. **End of campaign** → epilogue narration, victory/defeat stinger, a summary card with party image, stats, encounters won and time played; saves a final recap.

- **Chat** takes about 60% of the width, the right column about 40%. DM bubbles are on the left, player bubbles on the right, each tinted to that player's color with their character's avatar. Streaming text appears as it arrives. The sentence being spoken is subtly highlighted. Roll results and state changes (e.g. "Brann −4 HP", "Clue found: matchbook from the Blue Lantern") appear as compact system chips.
- **"Speaking as" chips** pick which player is talking. Since everyone shares one machine, the active player is also auto-selected when the DM addresses a character by name or asks that player for a roll.
- **Roster cards**: thumbnails for everyone in the current scene (party, NPCs, enemies). Clicking a thumbnail opens the full-size card. **Stats** flips the card (3D flip) to show stats, HP, abilities, gear and history/lore. NPCs and enemies are added and removed **live** by the DM's tool calls (§10). Defeated or departed entries animate out. Party members always stay.
- **Scene image**: the current location or story moment. It crossfades in when ready, and while loading it shows the previous scene with a subtle "painting the scene…" shimmer (never a blank box).
- **Game state**: campaign goal with a progress bar, act/beat tracker, encounters won/lost, per-player HP and conditions, clues/items found, and a pacing indicator (on track / running long).
- **Responsive**: under ~900px the right column turns into tabs (Roster · Scene · State) above the chat. Mobile works but isn't the primary target.
- **Visual design**: polished, atmospheric and dark-themed by default, with a **per-campaign theme** (accent colors, display font, bubble texture) declared in the campaign file. Fantasy gets parchment and gold, noir gets smoky monochrome with neon accents, space gets cool HUD-glass. Load the `frontend-design` mindset: make it beautiful, not templated.

## 6. Rules: light d20 system (`core/rules.md`)

*Assumed default: fast enough for a 30–60 minute session and works in any genre.* The **engine** applies the rules. The DM model never does the math.

- **Six stats**: STR, DEX, CON, INT, WIS, CHA. Modifiers range from −1 to +3, set by archetype arrays plus a +1 the player chooses.
- **Checks**: d20 + modifier (+2 if proficient) vs DC: Easy 10 · Moderate 13 · Hard 16 · Heroic 19. **Advantage/disadvantage** means roll 2d20 and keep the higher/lower. A natural 20 is a crit success, a natural 1 a complication.
- **Combat**: initiative is optional (narrative turn order by default). Attacks are d20 + mod vs the target's Defense. Damage comes from weapon tier (d4/d6/d8/d10 + mod). **HP** = 10 + CON×2 + archetype bonus. At 0 HP a character is *Downed*: allies can stabilize them with a WIS check DC10, otherwise they get one more round before *Out of the fight* (no permadeath unless the campaign enables it).
- **Signature ability** per archetype, usable once per act.
- **Heroic Point**: each player starts with 1 and can spend it to reroll or add +5. The DM can award more for great roleplay.
- **No leveling**: one "milestone boost" (+1 stat or new trick) at the midpoint act.
- Campaign packs can **override or extend** these rules (e.g. noir adds *Nerve*, space adds *Oxygen*). See §13.

The engine exposes `resolveCheck`, `resolveAttack`, `applyDamage`, `heal`, `addCondition` and similar as pure functions with thorough unit tests, including statistical tests on the dice RNG.

## 8. Character creation (`core/character-creation.md`)

The same structured questions for every campaign, defined in markdown so the owner can edit them. Each question has an id, type (choice/text/multi), whether it's required, and whether "Surprise me" is allowed.

1. Player name (real person, for the "speaking as" chip) and player color.
2. **Archetype** (cards showing the campaign's re-skin).
3. **Character name** (required; offer "Suggest names" from the AI, matched to genre).
4. Pronouns.
5. Appearance: age range, build, skin/hair/eyes, one striking feature (optional / surprise me).
6. Outfit & style (optional).
7. **Signature weapon or item** (optional; describe it).
8. **Companion** (optional): a pet, familiar, droid or sidekick, with its name and description. A companion can be a **full party member** that a human controls and rolls for (e.g. the family dog as a character). Companions appear in portraits and the party image, and get their own roster card.
9. Personality trait and one flaw or fear.
10. Backstory hook: pick one of the campaign's hooks or write your own.
11. +1 stat bump.

The answers become a `Character` record (zod schema) stored with the session.

## 9. DM style & standard process (`core/dm-style.md`)

This is the standardized "language" of the game. Campaigns can tweak tone but not this structure.

- Second person, vivid but **brief**: 2–5 sentences of narration per beat, then a clear prompt. It's spoken aloud, so no walls of text and no markdown tables in narration.
- **Always end a turn by addressing a specific character by name** or the whole party, with an open question or 2–3 suggested options.
- Ask for rolls only when failure is interesting. Rolls are requested via a tool call, never invented.
- Rotate the spotlight fairly between players (the engine tracks spotlight counts and tells the DM).
- Follow the campaign's act structure and pacing hints (§10.4). Never stall, and always move toward the goal.
- Keep NPC voices distinct. Wrap spoken NPC dialogue as `«Name: line»` so TTS can switch voices.
- Content rating defaults to PG-13 and is configurable per campaign.
- Never reveal hidden campaign info (secrets, twists) until the story earns it.

## 10. The AI Dungeon Master

### 10.1 Provider abstraction (`src/ai/providers`)
One interface for every text provider:
```ts
interface TextProvider {
  id: 'anthropic' | 'openai' | 'gemini' | 'openrouter';
  listModels(): Promise<ModelInfo[]>;
  stream(req: ChatRequest): AsyncIterable<StreamEvent>; // text deltas + tool calls + usage
}
```
- **Anthropic** is the default. Browser calls need the `anthropic-dangerous-direct-browser-access: true` header. Use **prompt caching** on the large stable prefix (core rules + DM style + campaign pack + characters) to cut cost.
- OpenAI, Gemini and OpenRouter adapters use their native tool calling. If a model lacks tool calling, fall back to a fenced JSON block parsed with zod.
- Verify CORS behavior for each provider and show a clear error in Settings if a provider blocks browser calls.
- **Mid-game model switch**: the dropdown in the top bar changes the DM model on the next turn. Conversation state is provider-neutral, so switching providers works too.
- Show a small per-session cost/token meter (estimated from usage events).

### 10.2 DM turn protocol (structured tool calls)
The DM streams **narration as text** and changes game state **only through tools**. The engine validates every call (zod) and applies it. Invalid calls get an error result fed back to the model.

| Tool | Purpose |
|---|---|
| `request_roll` | `{character, kind: check/attack/save, stat, dc?, target?, reason, advantage?}` pauses for dice |
| `apply_damage` / `heal` | HP changes (engine computes from roll outcomes where relevant) |
| `add_condition` / `remove_condition` | |
| `roster_add` | introduce an NPC/enemy from the cast file (by id) or improvise one (name, look, stats) |
| `roster_remove` | `{id, reason: defeated/fled/left/ally_departed}` |
| `scene_change` | move to a location id from the world file (triggers music mood + scene image) |
| `advance_progress` | complete a beat or milestone, update the goal bar |
| `record_clue` / `give_item` | |
| `encounter_result` | `{encounter_id, outcome: won/lost/avoided}` |
| `set_music_mood` | explicit mood override (combat, tension, calm, triumph…) |
| `request_image` | ask the Art Director for a moment image (e.g. "the vault door opens") |
| `end_campaign` | `{outcome, epilogue_hint}` |

Roll flow: DM calls `request_roll` → UI shows the roll prompt for that character (3D dice or physical-dice entry) → engine resolves → result goes back to the DM as the tool result → DM narrates the outcome.

### 10.3 Context management
- The system prompt is core rules, DM style, the campaign pack (minus the secrets section until revealed, or include it marked "hidden"; your design choice, documented), the party sheets, and the current engine state snapshot.
- Keep the last N turns verbatim. Older turns are compressed into a **rolling summary** by the helper model, which bounds cost and latency over a 60-minute game.

### 10.4 Pacing
The engine tracks real elapsed time against the campaign's target length and each act's time budget. Each turn it injects a short pacing note (e.g. "Act 2 of 3, 14 min left in budget; begin steering toward the warehouse confrontation"). Near the end it tells the DM to move to the climax and wrap up.

## 11. Voice, speech input, music & sound

### 11.1 Text-to-speech (pluggable, great quality by default)
- Adapters: **OpenAI TTS** (default, natural voices, streaming), **ElevenLabs** (premium, per-NPC voices), **Browser SpeechSynthesis** (free fallback, used automatically if no key).
- Narration is split into sentences as it streams and the first sentence plays immediately, so there's minimal wait.
- **Voice casting**: one narrator voice, plus optional distinct voices for NPCs (`«Name: …»` markers), assigned automatically from the provider's voice list and overridable in the roster card.
- Controls: voice on/off, speed, skip current line. Pressing the mic **interrupts** the DM (barge-in).
- Music ducks under speech.

### 11.2 Speech input
- **Push-to-talk** (hold button or spacebar when the text box isn't focused), plus an optional toggle mode.
- Adapters: **Web Speech API** (free; Chrome/Edge) and **OpenAI transcription** (works in every browser, better accuracy). Auto-pick based on browser support and keys.
- The transcript lands in the input box for a quick edit, or auto-sends (setting).

### 11.3 Music & ambience
- **Mood-based music manager**: moods are `title, exploration, tension, combat, calm, mystery, triumph, defeat`. Crossfades between tracks, loops seamlessly, volume and mute in the top bar.
- **Bundled tracks** must be real and finished (no silence or beeps). Pick one approach and document it in `public/content/audio/LICENSES.md`:
  1. **Preferred:** source **CC0 / public-domain** loopable tracks (e.g. OpenGameArt CC0, Freesound CC0) covering each mood across fantasy, noir-jazz and sci-fi palettes. Record title, author, URL and license for every file.
  2. **Or** compose original tracks with code (`scripts/generate-audio.ts`, e.g. Tone.js offline rendering → OGG), committed with the generator source so they can be re-rendered.
  At least one track per mood, plus genre-specific variants for the three starter campaigns. Also dice-roll SFX, UI clicks, and victory/defeat stingers.
- **Per-campaign audio mapping** in `campaign.md` front matter: each mood maps to a bundled track id **or** to a file in the campaign's `audio/` folder. Users can also **upload their own files** per campaign per mood in the Campaign library (stored in IndexedDB), and those override the defaults.

## 12. Sessions, saves & recaps

- **Autosave** the full session (engine state, characters, chat log, roster, image references, settings snapshot) to IndexedDB after every turn.
- **Save & quit** asks the helper model to write **`recap.md`** — a single document from which the AI can resume the game quickly:
  ```markdown
  ---
  recap_version: 1
  campaign: ashes-on-45th-street
  saved_at: 2026-11-14T19:05:00-08:00
  elapsed_minutes: 27
  act: 2
  ---
  # Story so far           (5–10 bullet beats)
  # The party              (each PC: name, archetype, HP, conditions, gear, companion, notable choices)
  # Where we are now       (location id, scene situation, who's present)
  # Open threads & clues
  # NPC attitudes          (id → friendly/hostile/unknown + why)
  # Progress               (beats completed, encounters won/lost, goal %)
  # Next beat              (what the DM was about to do)
  # Engine state           (fenced JSON block with the exact machine state)
  ```
- The recap is stored with the session and offered as a download. **Home → Load recap file** rebuilds a session from it alone (the JSON block restores exact state, and the prose primes the DM), so the user can resume on another machine.
- **Export/import full session** as JSON too, for backups.

## 13. Campaign content pack format (the authoring scheme)

Every campaign is **one folder with exactly five files plus an optional `assets/` folder**. All files are markdown with YAML front matter: easy to write by hand or with Claude, and strictly validated by `npm run validate:campaigns` (also shown in-app when importing).

```
campaigns/<campaign-id>/
├─ campaign.md   # manifest + overview, goal, acts & beats, endings, theme, audio map
├─ world.md      # locations (with image prompts), factions, lore, tone
├─ cast.md       # NPCs & enemies with stat blocks, looks, history, tactics
├─ rules.md      # campaign-specific rule overrides/additions + archetype re-skins
├─ secrets.md    # twists, hidden truths, solutions; DM-only, revealed by triggers
└─ assets/       # optional: key-art.jpg, music/*.ogg overrides, pre-made images
```

### `campaign.md` front matter (example)
```yaml
---
id: ashes-on-45th-street
title: Ashes on 45th Street
genre: noir-mystery
era: 1931, a rain-soaked American city
tagline: A fire, a missing heiress, and a city that doesn't want answers.
players: 1-4
target_minutes: 45
content_rating: PG-13
art_style: "cinematic 3D, realistic lighting, 1930s film-noir palette, rain, neon reflections"
theme: { accent: "#c9a227", background: "#0d0f12", display_font: "Limelight", bubble: smoke }
audio:
  title: bundled:noir-title
  exploration: bundled:noir-streets
  tension: bundled:noir-tension
  combat: bundled:generic-combat
  mystery: assets/music/clue-piano.ogg
  triumph: bundled:stinger-victory
goal: { text: "Find out who set the Hartwell fire and recover Evelyn Hartwell.", milestones: 5 }
acts:
  - { id: act1, title: "The Fire", minutes: 12, beats: [arrive-scene, meet-chief, first-clue] }
  - { id: act2, title: "The Trail", minutes: 18, beats: [blue-lantern, docks-chase] }
  - { id: act3, title: "The Truth", minutes: 15, beats: [warehouse, confrontation] }
endings: [justice, deal-with-the-devil, too-late]
hooks: ["You owe the Hartwells a debt.", "The fire killed your informant.", "You were paid to look the other way."]
---
## Overview
(free prose: premise, the opening scene the DM should narrate, the feel)
## Beats
### arrive-scene
(what happens, what players can discover, what success/failure leads to)
...
```

The other files follow the same pattern: front-matter arrays with stable `id`s, plus prose sections per id. `world.md` locations include `image_prompt` and `music_mood`. `cast.md` entries include `name, role (ally/neutral/enemy/boss), look (for image prompts), stats, hp, defense, attacks, abilities, tactics, history`. `rules.md` holds `archetype_skins` (name, flavor, gear, ability flavor per archetype) and optional `extra_rules`. `secrets.md` holds entries with `reveal_when` triggers.

Claude Code must produce:
- **zod schemas** for all five files, plus helpful validator errors (file, line, field, and a fix suggestion).
- **`docs/CAMPAIGN_AUTHORING.md`**: the full spec, a blank template for each file, a complete annotated example, and a **copy-paste prompt** the owner can give Claude (in chat) to generate a new campaign pack in exactly this format, e.g. *"Write a TaleForge campaign pack for a 40-minute Western ghost story for 2–3 players. Output the five files…"*.
- **Import flow**: drag a campaign folder or `.zip` into the Campaign library → validate → store in IndexedDB → appears in the picker. Bundled campaigns load from `public/content/campaigns`.
- **Three complete, high-quality starter campaigns** (fantasy, noir, space), each fully playable in about 45 minutes with 3 acts, 6–8 beats, 6+ cast entries, a boss, multiple endings, real key art (see §14) and an audio mapping.

## 14. Images: the Art Director agent (`src/ai/art`)

A background service that writes prompts, queues jobs, caches results and feeds images to the UI without blocking gameplay.

**Image provider abstraction**:
```ts
interface ImageProvider {
  id: 'openai' | 'gemini' | 'stability' | 'replicate' | 'custom';
  listModels(): Promise<ModelInfo[]>;
  generate(req: { prompt; size: 'portrait'|'landscape'|'square'; references?: Blob[]; }): Promise<Blob>;
}
interface VideoProvider { /* stubbed interface only; implement later */ }
```
- **OpenAI is the default** (current image model fetched from the model list). Also implement **Gemini**. Add a **"Custom endpoint"** adapter configured in Settings: URL, auth header, request template with `{{prompt}}/{{width}}/{{height}}`, and a JSON path to the image or base64 in the response, so any other provider can be connected without code. Each one gets a "Test" button.
- Use **reference images** for consistency where the provider supports it: every scene featuring the party passes the confirmed character portraits as references.

**What gets generated, and when:**
1. **Character portraits** (portrait orientation, full body, "3D fantasy to realistic" style, adapted to the campaign's `art_style`). Shows archetype gear, signature item, outfit, features and companion. Queued the moment each character is confirmed.
2. **Name plaque**: render it **in the app**, not in the image prompt, as a styled plaque composited onto the portrait with canvas/SVG. Spelling is always correct and the style matches the campaign theme. The composited image is cached as the card art.
3. **Party image** (landscape): all characters together in the campaign's opening environment, using the portraits as references. Queued as soon as all portraits exist.
4. **Scene prefetch**: at game start, queue images for the first 2–3 locations from `world.md`. On every `scene_change`, queue the **next likely** locations (from the act/beat graph). Some scene images include the party (more personal), others are pure environment (faster, cheaper).
5. **NPC/enemy portraits** for cast entries likely in the next act, plus on-demand portraits for improvised NPCs.
6. **Moment images** from `request_image` (best effort; shown when ready with a gentle "new image" pulse, never blocking narration).

**Mechanics:** priority queue (portraits > current scene > next scene > moments), concurrency limit (setting, default 2), retries with backoff, cost counter, and an IndexedDB cache keyed by a hash of prompt + provider + model. The helper model writes the prompts from structured inputs (character record, location entry, art_style), so prompts stay consistent. If no image provider is configured, the app uses each campaign's bundled key art and the archetype SVG cards, and stays fully usable.

## 15. Dice

- **Setup choice**: Digital / Physical / Per player. Toggle anytime from the top bar.
- **Digital**: a physics-based 3D dice tray overlay (d4, d6, d8, d10, d12, d20, d100). The player **clicks the die (or presses Space) to throw**. Throw strength and spin vary with mouse/drag velocity, and the dice tumble, bounce and settle with sound. **The face that lands up is the result.** If you use a predetermined-result approach instead, the value must come from `crypto.getRandomValues` and the animation must land on that face. Either way, rolls must be fair, and unit tests check the distribution (chi-square over many rolls).
- **Physical**: a roll prompt card ("Brann, roll a **d20** for a STR check, DC 13") with a big number pad sized for the requested die, input validation (1–20 etc.), and an "I rolled twice (advantage)" option.
- **Free rolls**: a dice button for players to roll anything outside a request (shown in chat).
- Results animate into the chat as roll cards showing the math (`17 + 2 + 2 prof = 21 vs DC 13 ✔`).
